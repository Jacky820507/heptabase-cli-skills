# 給未來 session 的信

我是這次建置這套治理系統的 session（Fable 5，2026-07-03）。這是我唯一一次跑這個 repo 的機會，寫這封信是為了讓你——不管你是 Sonnet、Haiku 還是別的模型——知道我沒有明講在規則裡、但你應該知道的事。

## 三件使用者沒問，但我認為重要的事

**1. `sync-github.ps1` 的白名單問題我已經修了，但這類問題會再發生。** 我在盤點時發現這支發布腳本的 `$PathsToStage` 陣列漏掉了這次新建的 `CLAUDE.md`／`.claude/`，已經加進去了。但這個陣列本質上是手動維護、沒有任何機制會自動偵測新增的頂層路徑——下一次有人在 repo 根目錄加東西，一樣可能忘記檢查這個陣列。`diagnosis.md` 案例 2 講的是這個問題本身，但沒有辦法從根本解決「手動白名單會過時」這件事，只能提醒你每次都要檢查。

**2. `sync_upstream.bat` 裡寫死了絕對路徑 `E:\Github Library\heptabase-cli-skills`。** 這代表這支腳本只能在使用者這台機器、這個確切路徑下work。如果使用者換機器或搬動 repo 位置，這支腳本會靜默失敗（`cd /d` 到不存在的路徑）。我沒有動它，因為這是使用者的私人自動化，不是我該擅自「修好」的東西——但如果使用者哪天抱怨「自動同步好像沒在動」，這是第一個該檢查的地方。

**3. 兩份 plugin manifest 的版本號同步，目前完全只靠 `CONTRIBUTING.md` 裡的一句話約定，沒有任何自動化強制。** `CONTRIBUTING.md` 說 `.cursor-plugin/plugin.json` 的版本要跟 `.claude-plugin/plugin.json` 保持一致，但沒有 CI 檢查、沒有 pre-commit hook 檢查這兩個數字是否真的相等。這是一個「規則寫在文件裡但沒有機制強制」的典型例子——如果你有能力，這其實是一個值得建議使用者加進 `.github/workflows/validate-skill-and-marketplace.yml` 的檢查（目前那個 workflow 只驗證格式，不比對兩份版本號是否一致），但我沒有動 CI 設定，因為那超出這次「建立文件治理」的範圍，也屬於 `maintenance.md` 表格裡「動之前要先問」的項目。

## 這套制度最可能怎麼退化，以及怎麼預防

**最可能的退化方式**：`CLAUDE.md` 的索引表與 repo map 會隨著時間過時——新增一個 skill、新增一份治理文件、新增一支腳本，卻沒有人回頭更新 `CLAUDE.md`。索引一旦跟實際狀態脫節，弱模型會照著過時的索引去讀不存在的東西，或漏掉真正該讀的新文件，整套系統的「先讀索引再行動」就失效了。

**預防法**：把「更新 `CLAUDE.md`」當成「新增頂層檔案／目錄」這件事本身「做完」的一部分，而不是事後才想到的補充動作——這件事已經寫進 `CLAUDE.md` 硬規則第 6 條，但規則寫著不代表會被照做，真正防得住退化的是**每次做這類變更時，把「有沒有更新索引」放進驗收條件**（見 `judgment.md` 第 2 條「何時算真的完成」）。次要的退化路徑：`.claude/commands/dispatch-*.md` 這五支指令如果沒人記得存在，會被閒置——`CLAUDE.md` 跟 `handoff-templates.md` 都有提到它們，但如果連 `CLAUDE.md` 都沒被讀過，這些指令一樣會被遺忘。

## 誠實列出這次哪些產出信心最低

- **`diagnosis.md` 的三個案例是我讀檔讀出來的，不是實測量出來的。** 我沒有真的跑過一次完整的發版流程去確認「新檔案真的會被 `sync-github.ps1` 漏掉」，是從讀腳本原始碼推斷的——邏輯上應該站得住腳（`git add -- $PathsToStage` 明確只加陣列裡的路徑），但沒有實際執行驗證過。
- **`dispatch.md` 裡「升降級路徑」的「同一件事最多重試兩輪」是我定的預設值，沒有被這個 repo 的實際使用情況驗證過。** 這個數字合理，但如果你發現兩輪太嚴格或太寬鬆，直接改掉這條規則，不用覺得這是我盤點出來的「事實」——這是我提議的政策，不是查證出來的結果。
- **`dispatch.md` 裡列出的 subagent 型別清單（`Explore`、`claude-code-guide` 等）跟 model ID 對照表，都是我在這次 session 環境裡觀察到的快照，不是查閱穩定文件得到的保證值。** 我在文件裡加了「可能過時，用之前重新確認」的提醒，但這是我對這套治理系統整體信心最低的一塊——harness 層級的東西變動不在這個 repo 的掌控範圍內，如果你發現這張表整個對不上，不代表這份治理系統壞了，只代表這部分需要重新查證更新。
- **`handoff-templates.md` 跟五支 `/dispatch-*` slash command 的設計（不用 `context: fork`，讓目前 session 先填空再手動呼叫 `Agent`）是我的判斷，沒有在這個 repo 裡實際跑過一輪完整流程驗證好不好用。** 如果用起來覺得綁手綁腳，這是最適合依實際使用經驗調整的一塊，調整後記得寫回 `lessons-learned.md`。
