# 判斷力外化

以下五條，每條都是：**判準（問句形式）→ 決策程序 → 一正例一反例**。如果讀完一條還是不知道該怎麼做，代表這條寫得不夠具體，回頭把它改具體，不要憑感覺行動。

## 1. 何時該升級模型

**判準**：這次失敗，是「操作有誤」還是「理解有誤」？

**決策程序**：
1. 看錯誤本身：是格式/語法/路徑打錯（操作有誤），還是做出來的東西邏輯上不符合需求（理解有誤）？
2. 操作有誤 → 同一模型修正後重跑一次即可，不必升級。
3. 理解有誤 → 立刻升級，不要在原模型上再試第二次「理解同一件事」。升降級的機制細節見 [`dispatch.md`](dispatch.md) 的「升降級路徑」。

- **正例**：subagent 把 `heptabase note save` 的 `--content-md5` 參數打錯位置，指令直接報錯——這是操作有誤，修正參數順序後同模型重跑。
- **反例（不該做的事）**：subagent 生成的 ProseMirror JSON 語法沒錯，但完全誤解了「原文卡不能加 AI 評論」這條規則，混進了摘要內容——這是理解有誤，不該只是「叫它再檢查一次」，要升級並在 prompt 裡明講「原文卡與整理卡的差異是什麼、為什麼」。

## 2. 何時算真的完成

**判準**：驗收條件是否**逐條**被獨立驗證過，而不是執行者自己說「應該可以了」？

**決策程序**：
1. 回頭看任務交辦時寫的驗收條件（沒有寫驗收條件的任務，先補寫再判斷，見 [`handoff-templates.md`](handoff-templates.md)）。
2. 每一條驗收條件，是否有一個**不是原執行者**的來源確認過（fresh-context 讀回、實際跑指令、或指揮官自己檢查）？
3. 全部條件都確認過 → 完成。有任何一條只靠執行者自陳 → 還沒完成，缺這一步不能算做完。

- **正例**：改完 `skills/heptabase-cli/SKILL.md` 的某個範例後，實際跑 `npx --yes skills-ref validate ./skills/heptabase-cli` 拿到通過的輸出，才回報完成。
- **反例（不該做的事）**：改完就說「應該符合 skills-ref 規範」但沒有實際跑 validate 指令，直接回報完成——這是猜測，不是驗證。

## 3. 何時該停下來問使用者，而不是自己猜

**判準**：猜錯的代價，跟「停下來問一句」的代價比起來，哪個大？

**決策程序**（依序檢查，中一項就該問）：
1. 這個動作**不可逆**或**難以逆轉**嗎？（例如刪除、強制推送、動到使用者的私人腳本）→ 問。
2. 這件事**沒有寫在任何文件裡**，純粹是猜使用者意圖嗎？（例如 `silent_run.vbs` 該不該整理）→ 問。
3. 這件事**可逆**、**有明顯合理預設**、而且**猜錯的代價很低**（例如一份新 reference 文件的標題措辭）→ 不用問，直接做，做完在回報裡說明自己選了哪個預設、為什麼。

- **正例**：使用者說「幫我整理一下 repo 根目錄」，看到 `silent_run.vbs`／`sync_upstream.bat` 沒有文件、看起來像雜物——先問使用者這兩個檔案是不是還在用，而不是自己判斷「沒人管就是可以刪」。
- **反例（不該做的事）**：新增一份 `references/xxx.md`，因為不確定要不要在檔名用連字號還是底線，就跑去問使用者——這種有明顯慣例可循（這個 repo全部用連字號）、猜錯也只是重新命名一次的小事，不需要問，直接照現有慣例做。

## 4. 什麼訊號代表「方向錯了該換路」，而不是「再試一次就好」

**判準**：重複失敗的原因，每次都一樣，還是每次都不一樣？

**決策程序**：
1. 同一件事失敗第二次時，把兩次的錯誤原因並排看。
2. **原因相同或高度相關**（例如都是同一個誤解造成的）→ 這是「換路」訊號：停下來重新確認需求或去問使用者，不要用同一種方法再試第三次。
3. **原因彼此無關、各自是獨立的小失誤**（例如第一次是打錯路徑、第二次是漏加參數）→ 可以再試一次，但已經用完 `dispatch.md` 規定的兩輪重試上限後，一樣要停下來，不能無限重試。
4. 另一個獨立訊號：**驗收條件本身跟你觀察到的 repo 事實矛盾**（例如任務要求「把版本號改到跟 CLI 版本一致」，但這是兩個不相關的版本號，見 `diagnosis.md` 案例 1）→ 不管重試幾次都是錯的，這是需求本身有問題，直接停下來跟使用者確認，不要嘗試用重試解決需求層面的矛盾。

- **正例**：兩次嘗試把 gmail skill 的白名單邏輯改成「支援網域比對」都失敗，且兩次都卡在同一個地方（不確定 Gmail query 語法能不能表示網域萬用字元）——這是同一個理解缺口，該去查 Gmail 搜尋語法文件或問使用者，而不是第三次用同樣方式亂試。
- **反例（不該做的事）**：任務是「把兩份 plugin.json 版本號同步」，但需求裡寫的來源版本號其實是 `SKILL.md` 的 CLI 相容範圍——執行者發現數字對不上就一直嘗試各種「同步方式」重試三、四次，而不是停下來指出這兩個本來就是不同的東西。

## 5. 品質底線怎麼驗

**判準**：這個 repo 有沒有一個**現成、客觀**的檢查可以跑，而不是只能用肉眼判斷？

**決策程序**：
1. 改動涉及 skill／plugin 結構 → 一定要實際跑這三個指令（`CONTRIBUTING.md` 的 Release Checklist 與 CI workflow 用的是同一組）：
   - `npx --yes skills-ref validate ./skills/heptabase-cli`
   - `claude plugin validate .`
   - `node scripts/validate-cursor-plugin.mjs`
2. 改動是純文字/文件內容（例如 `.claude/docs/*.md`） → 沒有自動化指令可跑，改成「fresh-context 讀回 + 對照驗收條件逐條核對」，見上面第 2 條。
3. 不確定某類改動有沒有現成驗證指令 → 去讀 `.github/workflows/validate-skill-and-marketplace.yml`，那是這個 repo CI 實際在跑的東西，比憑印象猜可靠。

- **正例**：改了 `.cursor-plugin/plugin.json` 的版本號後，跑 `node scripts/validate-cursor-plugin.mjs` 確認格式正確，而不是只用眼睛看 JSON 語法有沒有明顯錯誤。
- **反例（不該做的事）**：改完 `skills/heptabase-cli/SKILL.md` 的 `allowed-tools` 欄位，覺得「語法看起來對」就回報完成，沒有實際跑 `claude plugin validate .`。
